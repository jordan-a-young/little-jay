# Verification matrix

Run commands from the repository root using pnpm. Scripts in `package.json`, test projects in `vite.config.ts`, CI in `.github/workflows/ci.yml`, and applicable scoped `AGENTS.md` files are authoritative. Use [the task-to-file map](REPO-MAP.md) to find affected tests and consumers.

## Select checks without repeating work

- Combine every applicable row below. Start with the smallest relevant test during development, then run the checks warranted by the final diff. Scoped requirements still apply.
- Build before standalone tests/typechecks on a fresh checkout: `pnpm build` is the documented baseline because consumers resolve built package exports. In an already-built workspace, rebuild changed libraries and their prerequisites before checking consumers. Reuse successful check results only if relevant source, configuration, dependencies, and build outputs have not changed.
- Browser iteration is different: playground/UI source and styles hot-reload through development exports and the source-CSS alias, without rebuilding or restarting. That does not update built exports/declarations or prove production/package behavior. Use focused checks during iteration and the combined final gates for the change type; see the [fast development loop](../AGENTS.md#fast-development-loop).
- Use `pnpm --filter '@littlejay/ui...' build` for a dependency-inclusive library build, replacing the name as needed. Use `pnpm --filter @littlejay/ui typecheck` for a scoped TypeScript check. Brand/tokens have no typecheck script, and no workspace has a test script; run focused tests through root `pnpm test <file-or-path>`.
- Stop task-owned development servers before clean builds. Do not replace outputs consumed by another task's servers; use an isolated source copy if needed. See [application guidance](../apps/AGENTS.md#isolated-development) for port and process ownership.

## Browser risk policy

- **Required:** New/custom controls; changes to rendered markup, styles, interaction, accessible semantics/names, keyboard/focus, responsive layout, themes/visual assets, or browser-specific routing/runtime wiring. Include browser-dependent API/Query states when their visible behavior changes. A native element, small diff, or passing jsdom test does not exempt custom styling or interaction changes.
- **Not required:** Prose/comments, tests, type-only declarations/exports, and behavior-preserving internal refactors when inspection and relevant automated checks establish unchanged rendered output, CSS, semantics, interaction, and browser wiring. Record the skip reason and supporting evidence. Public declarations/exports still trigger package-distribution checks; skipping a browser does not waive those checks.
- **Uncertain:** Run the smallest browser check that resolves the risk. Explicit task acceptance criteria and feature-specific checks still apply; this policy is not a waiver for required checks or unresolved failures.

### Representative checklist, not a Cartesian product

Before launching, record the affected flow, expected outcomes, required checklist items and environment in task context. Select only dimensions affected by the change:

1. Exercise each changed behavior/state once in a representative environment. For controls, cover relevant keyboard activation, accessible naming, visible focus and disabled/error behavior; include focused invalid states when supported. Check modal trapping/restoration and portal inheritance only when affected.
2. Sample affected visuals in light and dark themes once; do not replay the whole interaction suite in each theme unless theme changes affect behavior.
3. Check affected layout at one wide and one real narrow viewport, verifying actual dimensions, overflow and clipping. Do not repeat every state at each width unless there is a concrete state/layout interaction risk. The catalog width control is not a real viewport.
4. For new/changed component CSS or styling-distribution wiring, check one affected packaged/reset-free consumer flow. Reuse it for behavior/theme/layout evidence when it exercises the same changed feature; a second identical playground pass is unnecessary. Declaration-only exports need the automated package check, not a browser fixture. Development hot-reload or production/base-path changes still require the specific affected environments from the matrix.
5. Inspect relevant console errors/warnings and failed requests once at the end of the flow. Capture screenshots only for visual uncertainty or requested artifacts. Expand coverage only for a concrete risk, failure, explicit request, or feature-specific requirement.

Confirm server readiness before navigating. Select the task-owned tab before resizing or keyboard use; verify the actual viewport and intended focus target. Take one initial accessibility snapshot after readiness, then refresh only when needed for changed controls/accessibility evidence. Scope selectors to the feature and batch dependent interactions/assertions into fewer calls; do not concurrently mutate browser state or replace real keyboard behavior with synthetic events. Stop when the checklist passes; after fixes, rerun only affected checks. Record validation wall-clock start/end and elapsed time including browser setup, with significant blockers identified; no fixed time budget permits silently skipping required checks.

## Final integration and reporting

- `pnpm ready` is the full CI gate: read-only changeset validation, check, build, typecheck, coverage tests, package-consumer checks. `pnpm release:validate` checks existing notes without requiring any notes, writing release files or reading Git history. `pnpm test:coverage` runs the full suite with V8, requires at least 90% aggregate coverage for each of statements, branches, functions, and lines, and then validates the report's authored-source inventory through `scripts/check-coverage.mjs`. See [coverage scope and reports](../README.md#test-coverage). A threshold failure remains blocking even if all tests pass; do not lower thresholds or narrow the source denominator to hide it. Prefer the full gate for final source-change integration when practical; focused results are not equivalent to a full CI pass. Do not rerun its constituent checks immediately beforehand solely to duplicate coverage.
- Package-consumer checks create and retain a temporary consumer and may need registry access or an existing store. Use `TMPDIR=/tmp/opencode pnpm test:packages`, or `TMPDIR=/tmp/opencode pnpm ready` when running the full gate. If prerequisites are unavailable, report the blocked check rather than installing unrelated tools, bypassing checks, or claiming a pass.
- Packaged README/consumer-agent guidance changes require `pnpm check` and the package-consumer check, including README presence, packaged local links, and the opt-in `AGENTS.md` discovery fixture. Reuse unchanged build prerequisites; combine executable tooling changes with the root-tooling row. No browser rerun is needed for prose-only package guidance without changed UI/assets.
- When browser checks are required by the risk policy, automated jsdom tests and the catalog's width control do not replace them. Report what was exercised, actual viewport sizes, elapsed browser-validation time including setup, and gaps; when not required, report the skip reason and supporting automated evidence. Do not claim measured time savings without comparable timing evidence.
- Report commands and actual outcomes, plus required checks that failed, were blocked, or were not run. Distinguish targeted validation from the full gate and pre-existing failures from regressions. Do not claim source-change readiness while required checks remain blocked.
- Maintain this matrix and affected scoped guidance in the same change when commands, build prerequisites, test projects, or verification requirements change. Keep instructions aligned with manifests and CI; do not invent package scripts.
