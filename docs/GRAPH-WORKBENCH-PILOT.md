## Existing behavior that adoption must preserve

1. **Drafts and selection:** Edits stay in controlled application state and mark the graph dirty, clear executable-version selection and reset consent. Dirty graph switches/copy operations require confirmation; leaving the page has a dirty warning. Server draft saves carry an optimistic cursor. Polling updates catalogs without replacing current in-memory edits after initial loading. Keep control identities and values stable through rerenders and failed commands.
2. **Pinned configuration:** The current definition revision plus instance overrides determines effective configuration. Selecting a node clears pending adoption. Saving a new reusable revision does not update existing instances. Adoption requires explicitly selecting a revision of that same definition, previews current/proposed values, then intentionally clears that instance's overrides on confirmation. Do not add automatic adoption or partial binding merges.
3. **Exact model choice:** BindingFields owns staged connection/model/variant/accounting-policy choices. It resets dependent choices on selection changes and commits only after a successful server binding-resolution command. A stale/missing catalog or non-simulated connection disables adoption; server checks, not that disabled button, enforce admission. Defaults are explicitly copied, never silently followed. Preserve its keyed reset behavior and fieldset/legend grouping.
4. **Pending/error behavior:** Builder commands disable the outer fieldset while pending; binding resolution has its own disabled/busy fieldset. Errors/status copy and existing role semantics stay application-owned. Replacing a control must not create an extra submission, request, retry, announcement, or focus move.
5. **Authority and history:** Owner pairing, exact Origin/CSRF, runtime Zod schemas, numerical ceilings, immutable versions, saved-binding consent, operation accounting and recovery stay in Graph Workbench. Editing a draft must not mutate a completed run or historical v1 data. No real service/credential/inference access follows from component adoption.
6. **Focus and responsiveness:** Keep visible labels, native number/select/textarea semantics, Tab order and visible focus. The inspector is inline, not a modal; selection does not currently require a dialog or automatic focus transfer. Preserve the React Flow editor's separate Enter/Space/arrow-key/removal contract. Existing dark canvas styling and narrow viewport behavior are outside the control replacement scope. Source inspection does not prove actual focus, contrast or mobile rendering after adoption; those need fresh browser checks.

## Consumption and styling prerequisites

- Consumer uses React/React DOM **19.3.1**, compatible with UI's declared `^19.0.0` peers. Its pinned development toolchain is **Node 24.18.0 / pnpm 10.34.5**, distinct from Little Jay's Node 26.13.0 / pnpm 12.18.0. Verify actual packed declarations/builds under the consumer toolchain before claiming support; do not migrate its tools incidentally.
- There is **no existing `@ljay/*` dependency** in `apps/web/package.json`. Packages remain private and unpublished. Proposed local route: build/package current Little Jay UI, tokens and brand under Little Jay's own toolchain, then agree on durable local tarball locations and explicit transitive resolution for `@ljay/tokens`/`@ljay/brand` in the consumer. A UI tarball alone does not make its packed `0.0.0` private dependencies registry-resolvable. Do not introduce registry publication, Git-install assumptions, cross-repository `workspace:*`, symlinks, or dependency overrides without the adoption task's agreement.
- Load compiled `@ljay/ui/styles.css` once; no Tailwind installation/reset is needed. **CSS coexistence is an unverified adoption prerequisite:** consumer `.m8-page input/textarea/select` and application button rules are unlayered, whereas much of UI's compiled styling uses layers/utilities. Simply importing the stylesheet later will not reliably override those rules. Plan a narrowly scoped consumer stylesheet adjustment for adopted controls, preserving controls elsewhere, the application theme and React Flow. Do not broaden the pilot into a whole-app theme migration or change shared CSS to accommodate this single app.
- Start with the inspector's existing dark presentation; explicitly scope its UI theme/tokens and verify contrast, inherited fonts, sizing and outlines. Validate Little Jay's unchanged light/dark library behavior separately if shared styles are touched. Do not infer a consumer-wide light-theme feature.
- This slice uses no Pebble artwork. UI's transitive brand package does not grant artwork/trademark reuse rights; retain notices and reserved-rights statements.
