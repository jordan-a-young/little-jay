## Existing behavior that adoption must preserve

1. **Drafts and selection:** Edits stay in controlled application state and mark the graph dirty, clear executable-version selection and reset consent. Dirty graph switches/copy operations require confirmation; leaving the page has a dirty warning. Server draft saves carry an optimistic cursor. Polling updates catalogs without replacing current in-memory edits after initial loading. Keep control identities and values stable through rerenders and failed commands.
2. **Pinned configuration:** The current definition revision plus instance overrides determines effective configuration. Selecting a node clears pending adoption. Saving a new reusable revision does not update existing instances. Adoption requires explicitly selecting a revision of that same definition, previews current/proposed values, then intentionally clears that instance's overrides on confirmation. Do not add automatic adoption or partial binding merges.
3. **Exact model choice:** BindingFields owns staged connection/model/variant/accounting-policy choices. It resets dependent choices on selection changes and commits only after a successful server binding-resolution command. A stale/missing catalog or non-simulated connection disables adoption; server checks, not that disabled button, enforce admission. Defaults are explicitly copied, never silently followed. Preserve its keyed reset behavior and fieldset/legend grouping.
4. **Pending/error behavior:** Builder commands disable the outer fieldset while pending; binding resolution has its own disabled/busy fieldset. Errors/status copy and existing role semantics stay application-owned. Replacing a control must not create an extra submission, request, retry, announcement, or focus move.
5. **Authority and history:** Owner pairing, exact Origin/CSRF, runtime Zod schemas, numerical ceilings, immutable versions, saved-binding consent, operation accounting and recovery stay in Graph Workbench. Editing a draft must not mutate a completed run or historical v1 data. No real service/credential/inference access follows from component adoption.
6. **Focus and responsiveness:** Keep visible labels, native number/select/textarea semantics, Tab order and visible focus. The inspector is inline, not a modal; selection does not currently require a dialog or automatic focus transfer. Preserve the React Flow editor's separate Enter/Space/arrow-key/removal contract. Existing dark canvas styling and narrow viewport behavior are outside the control replacement scope. Source inspection does not prove actual focus, contrast or mobile rendering after adoption; those need fresh browser checks.

A UI tarball alone does not make its packed `0.0.0` private dependencies registry-resolvable. Plan a narrowly scoped consumer stylesheet adjustment for adopted controls, preserving controls elsewhere, the application theme and React Flow. - Start with the inspector's existing dark presentation; explicitly scope its UI theme/tokens and verify contrast, inherited fonts, sizing and outlines. Validate Little Jay's unchanged light/dark library behavior separately if shared styles are touched. Do not infer a consumer-wide light-theme feature.

### UI-002: candidate Tabs scope

**Evidence:** The legacy builder's Library/Canvas/Inspector controls choose which content region is visible below 700 px, while all regions can be visible at larger widths. This is stronger evidence for potential tabs than the unrelated graph-node/history `aria-pressed` selectors. No new Menu, Tooltip, ToggleGroup, shared validation package or snapshot/SSE abstraction was established by this inspection.

**Proposed Little Jay-only scope, pending approval:** A reusable accessible Tabs primitive with matching trigger/panel relationships, controlled/uncontrolled selection, keyboard focus/navigation, disabled-tab behavior, themed/reset-free styling and a local catalog example. Keep workflow state, graph rendering and responsive all-panels-versus-one-panel layout in the application; do not embed Graph Workbench labels, breakpoints or API calls in shared UI. Specify activation and inactive-panel mount/preservation behavior before implementation so complex canvas/form state is not lost or expensive content activated accidentally.

**Verification for an approved implementation:** Follow Little Jay's React/public API/CSS/package-distribution requirements: interaction regressions, strict installed declarations and public exports, both themes, keyboard and narrow browser flows, no global reset, package-consumer checks, coverage gate and independent final API review. Demonstrate the pattern in Little Jay's playground only; no Graph Workbench build, install, test, migration or live access is needed to implement the library capability. Eventual consumer adoption needs its own responsive/canvas-state verification and authorization.

**Assessment-time readiness:** Existing primitives covered the other inspected presentation needs through native/app-local composition. Tabs was a scoped candidate, not a confirmed mandatory dependency; its subsequent implementation is recorded below. Future graphs, large datasets, rich editors or new interactions need their own consumer evidence. This assessment does not claim that Little Jay already contains every component Graph Workbench will ever need.
